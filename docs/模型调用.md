# Grok 模型调用：两种方式

本项目答题曾经用过两种 Grok 调用路径，**不要混用**。

| | A. 官方 API | B. Grok CLI 代理（当前默认） |
|---|---|---|
| 地址 | `https://api.x.ai/v1/chat/completions` | `https://cli-chat-proxy.grok.com/v1/chat/completions` |
| 身份 | 控制台 API Key `xai-...` | `grok login` 写入的 session token |
| 凭证位置 | 环境变量 `XAI_API_KEY` | `~/.grok/auth.json` 的 `key` |
| 选模型 | JSON body 的 `model` | **Header** `x-grok-model-override`（body 里的 `model` 不决定路由） |
| 典型模型 | `grok-4.6` | `grok-build` |
| 流式 | 支持非流式、可要 JSON | 多数模型必须 `"stream": true`；`grok-build` 两种都支持 |
| Token 寿命 | 直到你在控制台撤销 | 约 7 天，过期后 `grok login` |
| 计费 | API 额度 | CLI 登录套餐 |
| 本仓库现状 | 设置了 `XAI_API_KEY` 时走这条（适合部署） | 未设置 Key 时走这条（适合本机 `grok login`） |

向量检索是第三件事（阿里云 Qwen embedding），见文末，和这两种 Grok 调用无关。

---

## A. 官方 API（`api.x.ai`）

面向产品、SDK、长期服务。正规做法是在 [console.x.ai](https://console.x.ai) 创建 API Key，**不要**把 `auth.json` 里的登录 JWT 当成 API Key。

### curl

```bash
export XAI_API_KEY="xai-..."

curl -sS https://api.x.ai/v1/chat/completions \
  -H "Authorization: Bearer $XAI_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "grok-4.6",
    "temperature": 0.1,
    "response_format": {"type": "json_object"},
    "messages": [
      {"role": "system", "content": "只输出 JSON"},
      {"role": "user", "content": "用 {\"ok\": true} 回答"}
    ]
  }'
```

OpenAI 兼容 SDK：

```python
from openai import OpenAI

client = OpenAI(api_key=os.environ["XAI_API_KEY"], base_url="https://api.x.ai/v1")
resp = client.chat.completions.create(
    model="grok-4.6",
    messages=[{"role": "user", "content": "Hello"}],
)
print(resp.choices[0].message.content)
```

### 曾经的权宜之计（不要再当主路径）

没有 API Key 时，有人会把 `~/.grok/auth.json` 里的 JWT 填进 `api_key=` 去打 `api.x.ai`。本仓库早期 RAG 就是这样。它**不是**官方 CLI 文档的用法，也没有 `X-XAI-Token-Auth` 等头。能通只是服务端碰巧接受了这张 JWT。

## B. Grok CLI 代理（当前答题路径）

模拟 Grok 终端内部请求。官方说明：用 `grok login` 存下的凭证，经 CLI chat proxy 调用。

### 必带头

| Header | 是否必须 | 作用 |
|---|---|---|
| `Authorization: Bearer <token>` | 是 | `auth.json` 里的 session token |
| `X-XAI-Token-Auth: xai-grok-cli` | 是 | 告诉中间件按 CLI session 校验，而不是 API Key |
| `x-grok-model-override: <model>` | 是* | **真正选模型**。`grok-build` 在默认路由上可省略，建议始终带上 |
| `x-grok-client-version: 0.1.202` | 实际必须 | 文档示例未写。不带时代理返回 **426**：`Grok CLI version (none) is outdated` |
| `User-Agent: grok-shell/0.1.202` | 建议 | 与 CLI 客户端一致 |

\*文档原文：proxy 用这个 header（不是 JSON body）把请求路由到对应后端。

### 取 token

文档示例：

```bash
jq -r '."https://accounts.x.ai/sign-in".key' ~/.grok/auth.json
```

本机 Grok CLI 1.0.x 实际可能是：

```text
https://auth.x.ai::<uuid>
  key: <JWT>
  expires_at: ...
```

代码（`_cli_session_token()`）先读文档路径 `https://accounts.x.ai/sign-in`，没有再遍历任意带 `key` 的项。

### curl（与文档一致，补上 version 头）

```bash
TOKEN=$(jq -r '."https://accounts.x.ai/sign-in".key // (to_entries[] | .value.key? // empty)' ~/.grok/auth.json | head -1)

curl -sS -N -X POST "https://cli-chat-proxy.grok.com/v1/chat/completions" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $TOKEN" \
  -H "X-XAI-Token-Auth: xai-grok-cli" \
  -H "x-grok-model-override: grok-build" \
  -H "x-grok-client-version: 0.1.202" \
  -H "User-Agent: grok-shell/0.1.202" \
  -d '{
    "model": "grok-build",
    "messages": [{"role": "user", "content": "Hello!"}],
    "stream": true
  }'
```

### 流式

多数 CLI 代理模型只支持流式，文档要求默认 `"stream": true`。

| 模型 | 非流式 | 流式 |
|---|---|---|
| `grok-build` | 支持 | 支持 |

SSE 里每一行 `data: {...}`：

- `choices[0].delta.reasoning_content`：思考过程，**不要**拼进最终答案
- `choices[0].delta.content`：真正回复
- `data: [DONE]`：结束

本仓库只拼接 `delta.content`，再从全文里解析 JSON（`answer` / `citations`）。

### 本仓库实现要点

文件：`pdf_rag/llm.py` → `chat_json()` → `_cli_chat()`。

- 用 **curl -N** 发请求（文档示例就是 curl）。本机 `httpx` 在 `HTTPS_PROXY` + `ALL_PROXY=socks5` 混用时，打这个域名容易 SSL 失败。
- 失败会重试最多 4 次。
- 模型默认 `GROK_CLI_MODEL=grok-build`，可用环境变量覆盖。

登录态过期（约 7 天）后：

```bash
grok login
```

## 两种方式不能混

| 错误做法 | 结果 |
|---|---|
| CLI 专用头打到 `api.x.ai` | 官方 API 不认这套中间件头 |
| 把 `xai-...` API Key 打到 `cli-chat-proxy` 且不带 `X-XAI-Token-Auth` | 中间件不当成 CLI session，常 401 |
| `auth.json` JWT 当 `api.x.ai` 的 API Key | 非文档路径，可能突然失效 |
| CLI 代理不带 `x-grok-client-version` | 426，提示 CLI 版本过旧 |
| CLI 代理用非流式调不支持非流式的模型 | 请求失败或空响应 |

## 和 RAG 其它调用的关系

一次提问：

1. **Qwen embedding**（阿里云 MaaS）：把问题变成 1024 维向量，和本地 `embeddings.npy` 做相似度。走 `.env` 的 `DASHSCOPE_API_KEY`，与 Grok 无关。
2. **本地 BM25**：关键词检索，不调模型。
3. **Grok 答题**（方式 B）：只把检索到的十几段原文发给 `grok-build`，流式拿回 JSON 答案和引用。

建索引时的 embedding 同样走阿里云，不走上面 A/B。
